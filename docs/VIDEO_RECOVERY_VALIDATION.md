# MP4/MOV recovery validation

This note covers the independent contiguous-video carver added for v0.1.3. It does not establish fragmented video reconstruction, camera-specific SD recovery, repair of missing metadata, codec integrity for arbitrary input, or equivalence with Recoverit.

## Original fixtures and local decoder evidence

Six small original clips are checked in under [`crates/recovery-core/tests/fixtures/video`](../crates/recovery-core/tests/fixtures/video). They contain a generated moving test pattern and a generated sine tone, with no third-party recordings or proprietary assets. The fixtures and generator use the repository's GPL-3.0-or-later license. FFmpeg's executable/libraries are not bundled or linked into Memory Regainer.

The reproducible [generator](../crates/recovery-core/tests/fixtures/video/generate.py) records complete commands, tool versions, SHA-256 hashes, probe results and decode exit codes in [manifest.json](../crates/recovery-core/tests/fixtures/video/manifest.json). Encoder versions can change regenerated bytes; the committed hashes identify these exact fixtures. Generation used FFmpeg/ffprobe 9.0.2, H.264/H.265 video, three 64×48 frames at 5 fps, and 0.6 seconds of synthetic audio.

| Fixture | Bytes | Layout and audio |
| --- | ---: | --- |
| `original-tail.mp4` | 5,879 | `moov` after media; AAC |
| `original-faststart.mp4` | 5,879 | `moov` before media; AAC |
| `original-tail.mov` | 12,475 | `moov` after media; PCM |
| `original-faststart.mov` | 12,475 | `moov` before media; PCM |
| `original-co64-extended.mp4` | 5,903 | Tail metadata, 64-bit `co64` offsets and extended-size `mdat`; AAC |
| `original-hevc.mp4` | 7,700 | Tail metadata, HEVC/H.265 `hvc1` with `hvcC`; AAC |

The fifth fixture is a documented independent transformation of the generated tail MP4: it replaces `stco` with `co64`, extends the `mdat` header by eight bytes, shifts chunk offsets by eight, and updates enclosing metadata lengths. It is not a hand-written imitation of the recovery parser. All six originals passed `ffprobe -count_frames` and a complete strict decode of every stream using `ffmpeg -xerror -err_detect explode -map 0 -f null -`, exit code 0. Each reports three decoded video frames and five decoded audio frames in the stored probe output.

## Public-API tests

[`tests/video.rs`](../crates/recovery-core/tests/video.rs) exercises `scan`, `read_entry` and `recover_entry` using checked-in bytes. No FFmpeg installation, downloads or physical-device access is needed in CI. It covers:

- Exact SHA-256 and byte equality after recovery of all six layouts, bounded preview reads, expected extent boundaries and unchanged source bytes.
- Unaligned headers across scanning-buffer boundaries; adjacent MP4/MOV files; extension-specific, case-insensitive filters; Quick versus Deep behavior.
- Selected ranges that exclude a header or final byte, plus a Unix sparse source containing a clip above the 4 GiB absolute offset with a narrow selected range. The latter does not benchmark a 4 GiB scan or validate media with actual 4 GiB chunk offsets.
- Truncated metadata/data, 32-/64-bit chunk offsets outside media, oversized samples, invalid sample-to-chunk references, timing/sample count disagreement and oversized declared tables.
- External data references, absence of a video track, encrypted sample entries, unknown/oversized file-type atoms, invalid sample-description references, duplicate sample tables, fragmented `moof` markers, zero-sized media atoms, overflowing extended sizes and cancellation without output.
- Truncated handler fixed fields with corrected parent lengths; missing AVC decoder configuration; visual-extension boundaries and AVC/HEVC parameter-set lengths that exceed their configuration atoms.

On 25 October 2026, all **24 public video integration tests passed** on macOS ARM64. The sparse-source test is Unix-only; Windows runs the other 23 tests. The round-trip test exported the actual recovered files to a temporary workspace directory. An independent Python/FFmpeg check confirmed all six exported SHA-256 hashes and bytes matched their originals, then fully decoded every stream with strict error handling: **six successful decodes, zero errors, 50,311 recovered bytes**. Exact hashes, codec/frame observations and exit codes are recorded in [video-recovery-evidence.json](video-recovery-evidence.json). These are core API results; native installer/runtime results are tracked separately in [VALIDATION.md](VALIDATION.md).

## Standards and interpretation

Apple specifies that chunk offsets are relative to the containing file, with `stco` and `co64` as alternate widths. An embedded recovered file therefore needs its candidate start added exactly once; a source offset must not be confused with a media-atom-relative offset. [Apple chunk-offset documentation](https://developer.apple.com/documentation/quicktime-file-format/chunk_offset_atom).

`stsc` maps samples to chunks, while `stsz` provides a default sample size or an explicit size table. Validating only a header or finding `moov`/`mdat` is insufficient: chunk/sample mappings must agree and their byte ranges must lie within available media payloads. [Apple sample-to-chunk documentation](https://developer.apple.com/documentation/quicktime-file-format/sample-to-chunk_atom), [Apple sample-size documentation](https://developer.apple.com/documentation/quicktime-file-format/sample_size_atom). Apple's sample-location procedure combines timing, chunk mapping, chunk offsets and sample sizes, supporting independent cross-table test cases. [Apple sample-location procedure](https://developer.apple.com/documentation/quicktime-file-format/using_sample_atoms).

Apple also defines the complete handler fixed fields and confines video sample-description extensions to their enclosing size. Regression cases preserve surrounding atom structure while truncating `hdlr` or damaging `avcC`/`hvcC`, so unrelated parser errors cannot make those tests pass accidentally. [Apple handler layout](https://developer.apple.com/documentation/quicktime-file-format/handler_reference_atom), [Apple video sample descriptions](https://developer.apple.com/documentation/quicktime-file-format/video_sample_description).

The application performs structural checks, not a codec decode. A file whose structure is coherent can still contain overwritten or undecodable media bytes. Successful decoding of these original synthetic examples establishes only these examples. It does not establish recovery from fragmented, overwritten, encrypted, truncated or physically failing USB media.

The current parser conservatively requires ordered, nonoverlapping chunk ranges within each track, explicit atom sizes, self-contained data references and an `ftyp` atom. Older MOV files without `ftyp`, fragmented MP4 and compressed movie metadata are outside scope. A carved candidate ends at the first complete container covering all declared samples; unreferenced trailing padding or unrelated extra atoms need not be retained. Candidate boundaries and codec integrity are distinct from knowing an original filename or filesystem allocation history.

## Reproduction

Generate and independently decode the fixtures locally:

```sh
python3 crates/recovery-core/tests/fixtures/video/generate.py
```

Run the portable tests without media tools:

```sh
cargo test -p recovery-core --test video
```

For a local independent decoder check of the actual recovery outputs, set `MEMORY_REGAINER_VIDEO_EXPORT_DIR` to a task-owned temporary directory when running `playable_mp4_mov_head_tail_and_co64_round_trip_exactly`. That test exports the six files it recovered after verifying their hashes. Run the manifest's full-decode command against each exported file, then remove that temporary directory. Normal tests leave no outputs.
